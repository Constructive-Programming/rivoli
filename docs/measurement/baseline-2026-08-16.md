# Decode baseline, 2026-08-16 — the numbers optimization gets measured against

One prompt, one release binary (`7df7d9b`, built once, never rebuilt between arms), one
GPU lock held across all three arms, `--test-threads`-style sole tenancy. The prompt asks
for a long technical essay (virtual memory + the GPU-memory comparison; ~80 tokens after
each model's framing), so all 512 generated tokens are real prose, not a repetition tail.

```
rivoli /var/db/rivoli/glm52-vq3-full            --bench 512 --max-mem 115 --prompt '<P>'
rivoli /var/db/rivoli/v4-f4-full                --bench 512 --max-mem 100 --ctx 2048 --prompt '<P>'
rivoli /swarm/storage/ai/rivoli/glimmer-30b-bf16 --bench 512 --max-mem 100 --prompt '<P>'
```

| arm | tok/s | decode wall | prefill | residency picture |
|---|---|---|---|---|
| GLM-5.2 int3-vq | **2.58** | 198.5 s | 82 tok, 28.7 s, 71.8% hit | 238,990 / 67,610 decode hits/misses (78%) |
| DeepSeek-V4 fp4 | **9.17** | 55.8 s | 82 tok, 7.3 s | 128,004 / 3,834 (97%) |
| Muse Glimmer bf16 | **2.56** | 200.0 s | 75 tok, 26.0 s | 52/52 layers pinned, 0 streamed |
| Kimi-K3 | — | — | — | **no checkpoint exists on this box or /swarm** |

## What each number says

- **V4 9.17 = 109 ms/token is exactly the old tree's recorded decode class** (its
  v4-decode-decomposition.md closed §M8 at 9.10–9.17). The rewrite carried V4's
  performance bit-for-bit, which also validates the method here.
- **GLM 2.58 vs the old tree's recorded 2.85** (async streaming + fp16 codebook, same
  artifact family): −9%. The rewrite has never been profiled — `Profile` was deferred to
  "the first benchmark", which is this one. First target.

  > **CORRECTED 2026-08-16 (M10), same day: −9% compares two different MODES.** `2.85` is
  > the old tree's **hybrid / lru** cell (`old:docs/measurement/benchmarks.md`, the 9-cell
  > matrix — "hybrid+lru wins ... its hot experts run int4's faster compute"). This row is
  > `--mode int3-vq`, and hybrid does not decode in this tree at all: it refuses at
  > `FormatPlan`. A mode the engine cannot express is not a regression it can have.
  >
  > **The like-for-like cell is `int3-vq / 2q`, and every condition matches** — same
  > artifact `/var/db/rivoli/glm52-vq3-full`, `--attn dense`, `--max-mem 115`, 512-token
  > greedy decode, release, sole-tenant, and this CLI's `--cache-policy` default is `2q`.
  > Only the prompt differs (the old matrix's was recorded verbatim; this row's was not —
  > see below).
  >
  > | | old tree, recorded | this row | Δ |
  > |---|---:|---:|---:|
  > | tok/s | 2.77 | 2.58 | **−6.9%** |
  > | decode wall | 361 ms/tok | 387.6 ms/tok | **+26.6 ms** (+7.4%) |
  > | misses/token | 132.7 | 132.05 | −0.5% |
  > | hit | 77.9% | 78.0% | +0.1pp |
  >
  > So the port gap is **−6.9%, not −9%**; ~2.6 points of the original figure is the
  > hybrid-vs-int3-vq mode difference. **And the last two rows say what it is NOT**: at
  > equal budget the rewrite misses the pool the same number of times per token and hits it
  > at the same rate, so the +26.6 ms is not more fetching and not worse residency. It is
  > host or compute time, which is what the phase profile localises — `PROFILE/tok` is now
  > always on and `tests/ppl-gates.sh`'s `profile` cell bounds it. **The named-phase
  > attribution of the 26.6 ms is the OWED half of this correction** and needs a device.
  >
  > Both old-tree numbers are re-derived here from that matrix's own table rather than
  > carried from prose (its wall column and its tok/s column agree: 1000/361 = 2.770,
  > 1000/351 = 2.849). The rewrite's misses/token is re-derived from this page's own
  > 67,610 over 512 tokens, and its hit from 238,990/(238,990+67,610).
  >
  > **FIRST PHASE PROFILE, 2026-08-17 — and it is NOT citeable against the row above.**
  > `tests/ppl-gates.sh profile`, same artifact/mode/attn/budget, 512 tokens:
  >
  > ```
  > PROFILE/tok: wall 543.261ms = attend 143.127 + ffn 205.681 + fetch-wait 186.155
  >                             + head 6.857 + other 1.440 (0.27% of wall)
  > DECODE: 512 tokens in 278.1 s = 1.84 tok/s | 241038 hits / 65562 misses
  > ```
  >
  > | | attend | ffn | fetch-wait | head | other |
  > |---|---:|---:|---:|---:|---:|
  > | ms/tok | 143.127 | 205.681 | 186.155 | 6.857 | 1.440 |
  > | share | 26.3% | 37.9% | **34.3%** | 1.3% | 0.3% |
  >
  > **1.84 tok/s, not 2.58** — 543.3 ms/tok against this row's 387.6, +40.2% of wall, at
  > 128.05 misses/token and 78.62% hit (this row: 132.05 and 78.0). *Fewer* misses, *better*
  > hit rate, 40% slower. **A foreign host tenant was running**: a `convert_k3` repack held
  > two processes at ~240% CPU each, loadavg 7.31 on 32 cores. The KFD witness did not see
  > it and cannot — it is not on the GPU — which is why `tests/gpu-witness.sh` now samples
  > host loadavg per arm and the `profile` cell prints an attribution caveat above 2.0.
  >
  > HYPOTHESIS, with its test, not a conclusion: if `attend + ffn + head` (355.7 ms) were
  > unchanged at this row's conditions, the implied clean `fetch-wait` would be **31.9 ms**,
  > i.e. **the entire +155.7 ms sits in fetch-wait** — which is what CPU/page-cache
  > starvation of the fetch reaper would do, and it does not require the miss COUNT to move.
  > **The test is one idle re-run**: if `fetch-wait` collapses toward ~32 ms and wall returns
  > to ~390, contamination is confirmed and the −6.9% above gets its phase attribution. If
  > it does not, `fetch-wait` at a third of wall is the real headline and the overlap this
  > engine is built on is not working. **Neither is established. The re-run is owed.**
  >
  > **And "idle" needs defining, because the obvious reading is wrong.** The tenant that
  > contaminated this run was a 1.4 TiB `convert_k3` repack, and it has finished — but the
  > box carries persistent load from SIBLING AGENTS running test suites: sampled
  > 2026-08-17 with the GPU free and zero KFD tenants, loadavg was **7.11 / 4.10 / 2.71**
  > (1/5/15 min), driven by another worktree's `v4_oracle` test binary at 144% CPU. So a
  > clean attribution number needs a COORDINATED quiet window, not merely the absence of
  > the one job everybody remembers. `tests/gpu-witness.sh` records per-arm loadavg for
  > exactly this reason, and the `profile` cell's caveat will fire on most casual runs of
  > this box — which is information, not noise.
  >
  > What the run DID establish, being a ratio and therefore load-immune: the buckets account
  > for the wall to 0.27%, the census is 3/3 non-zero, and the reported `other` re-derives
  > from the four buckets to 0.001 ms. The instrument is sound; the number it took is not
  > yet a measurement.
- **Glimmer 2.56 fully resident** is the softest number: ~53 GB of bf16 read per token at
  2.56 tok/s is ~135 GB/s effective against a ~256 GB/s bus. The artifact lives on NFS but
  every layer pins at this budget, so NFS costs load time only (26 s prefill includes it).
- **K3 has no row because no Kimi-K3 checkpoint exists anywhere reachable** — the largest
  model file on /swarm is a 20 GB GGUF. The only K3 that has ever decoded is the 5-layer
  synthetic correctness fixture, whose tok/s would be meaningless here. Obtaining the row:
  download the ~1.2 TiB checkpoint to /swarm (7.5 T free), run `convert_k3` (the MXFP4
  repack, output alongside — local NVMe holds ~173 G free, so both ends live on NFS), and
  accept that the routed-expert miss lane then streams over the network: the first K3
  number will carry an NFS asterisk until the artifact gets local storage.
